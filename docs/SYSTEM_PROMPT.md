## 1. ОБЗОР ПРОДУКТА

Веб-продукт для анализа межличностной совместимости, который объединяет четыре слоя:
1. **Астрологическая синастрия** (натальные карты, аспекты между картами, наложение домов).
2. **Нумерология** (число жизненного пути, судьбы/выражения, личные циклы, Матрица судьбы).
3. **Психология отношений** (Big Five/OCEAN, теория привязанности, «четыре всадника» и индекс восстановления Готтмана, MBTI как опциональный слой).
4. **Таро** (аркан-слой: аркан каждого партнёра, аркан пары и их взаимодействие — ещё одна «вселенная» совместимости, входящая в общий балл; см. §3.4а).

**Цель:** нешаблонные, информативные, практически применимые отчёты: процентные метрики, матрица рисков, зоны синергии и трения, план микропривычек для пары.

**УТП:** стираем грань между «развлекательной астрологией» и «психологией отношений» — красиво и легко подаём, но каждая рекомендация привязана к конкретному источнику (аспект, число, психологический параметр), а не к шаблонной фразе.

### Этическая рамка (обязательно)
- Астрология, нумерология и таро **не являются научно доказанными**. В продукте это честно обозначено («символический/рефлексивный слой»). Научно обоснованный слой — только психология (OCEAN, привязанность, Готтман).
- Таро подаётся как инструмент для размышления и разговора пары, а не как предсказание: никаких прогнозов смерти, болезней, измен, беременности, финансовых исходов и т.п.
- Продукт не даёт категоричных вердиктов вроде «вам нельзя быть вместе». Формулировки — «зоны внимания», «где потребуется договорённость».
- Дисклеймер в отчёте и в PDF; не медицинская и не терапевтическая услуга.
- Данные рождения и психопрофили — персональные: согласие, возможность удаления, шифрование чувствительных полей, соответствие 152-ФЗ и GDPR.

## 3. АРХИТЕКТУРА (SOLID + Clean/Hexagonal, готовность к масштабированию)

### 3.1. Слои и зависимости
Зависимости направлены **внутрь**: `interfaces → application → domain`. Домен не знает про Django, ORM, HTTP, Celery и LLM.

```
config/                  # settings (base/dev/prod), urls, celery, asgi/wsgi
apps/
  core/                  # общие value objects, исключения, утилиты, базовые интерфейсы
  profiles/              # профили партнёров, данные рождения, согласия
  astrology/             # расчёт натальных карт и синастрии
  numerology/            # нумерологические расчёты
  tarot/                 # аркан-слой: расчёт арканов, матрица пар 22×22, TarotScorer
  psychology/            # OCEAN, привязанность, Готтман, MBTI
  compatibility/         # оркестрация, скоринг, веса, отчёты
  knowledge/             # база знаний: блоки интерпретаций, источники, ревью, поиск
  insights/              # LLM-сшивка текстов, промпты, провайдеры, валидатор
  reports/               # рендер, PDF, шаринг по ссылке
  accounts/              # пользователи, авторизация, тарифы (на вырост)
```

Внутри каждого приложения единая структура:
```
<app>/
  domain/          # чистые сущности, value objects, доменные сервисы, интерфейсы (Protocol/ABC)
  application/     # use cases (сервисы приложения), DTO
  infrastructure/  # реализации интерфейсов: ORM-репозитории, эфемериды, LLM-клиенты, кэш
  interfaces/      # views, forms, serializers, templates, Celery tasks, admin
  tests/
```
Django-модели живут в `infrastructure/` (или `models.py` как тонкий слой), доменные сущности — отдельные dataclass/pydantic-объекты. Бизнес-логика **не** в views, **не** в моделях, **не** в сигналах.

### 3.2. SOLID — конкретно в проекте
- **S (Single Responsibility):** расчёт аспектов, нормализация оценки, генерация текста, рендер PDF — разные классы/модули. View только принимает запрос и вызывает use case.
- **O (Open/Closed):** каждый скоринг-модуль («вселенная»: астрология, нумерология, таро, психология) реализует единый интерфейс `CompatibilityScorer` и регистрируется в реестре. Новый модуль (например, хронотип, языки любви) добавляется **без правки** движка.
- **L (Liskov):** любой `Scorer` возвращает единый `ScoreResult` (значение 0–100, уверенность, факторы-«улики», риски); движок работает с ними взаимозаменяемо.
- **I (Interface Segregation):** узкие протоколы: `EphemerisProvider`, `GeocodingProvider`, `InsightGenerator`, `ReportRenderer`, `ProfileRepository` — вместо «толстых» сервисов.
- **D (Dependency Inversion):** use cases получают зависимости через конструктор; сборка — в composition root (`config/container.py`). Смена LLM-провайдера или эфемерид — замена одной реализации.

### 3.3. Паттерны (где уместны, без оверинжиниринга)
- **Strategy + Registry** — скореры и веса.
- **Repository** — доступ к данным из use cases.
- **Adapter** — LLM-провайдеры, геокодинг, эфемериды.
- **Pipeline** — сбор отчёта: расчёт → скоринг → факты-улики → LLM-текст → рендер.
- **Domain events** (лёгкие) — `ReportGenerated`, `ProfileUpdated`.

### 3.4. Движок скоринга
- Веса по умолчанию: **астрология 35% / психология 35% / нумерология 15% / таро 15%** (см. §3.4а). Пользователь настраивает ползунками.
- **Динамическое перераспределение:** если нет психоданных или времени рождения — веса пересчитываются пропорционально, а отчёт явно показывает «точность оценки» и что именно не учтено (например, без времени рождения не считаются дома и Асцендент).
- Каждый `ScoreResult` содержит **трассируемые факторы** («Венера A трин Марс B, орб 2.1°, вес +x») — LLM получает только их и не придумывает фактов.
- Расчётные снимки кэшируются (ключ — хэш входных данных + версия алгоритма).
- Формулы весов, шкалы и пороги — в конфиге/константах с тестами, а не «магическими числами» в коде.

### 3.4а. Слой Таро («аркан-слой») и принцип «Мультивселенной»
**Решение владельца:** таро — не отдельный модуль раскладов, а **ещё один слой совместимости** наравне с астрологией, нумерологией и психологией. Он отвечает на тот же вопрос — «насколько эти двое подходят друг другу» — со своей точки зрения.

**Как работает (детерминированно, без случайности).**
- Для каждого человека по дате рождения вычисляется его **аркан** (редукция даты к 1–22 по Старшим арканам). Конкретный метод редукции (суммирование цифр дня/месяца/года, правило для значений > 22) зафиксировать в ADR и тестах.
- Для пары вычисляются: аркан партнёра А, аркан партнёра Б, **аркан пары** (редукция суммы двух) и тип связи между арканами (одинаковые, дополняющие, «напряжённые», нейтральные и т.д. — правила записать в `docs/methodology/tarot.md`).
- `TarotScorer` реализует тот же интерфейс `CompatibilityScorer`: возвращает `ScoreResult` (0–100, уверенность, факторы-«улики», риски) и подоценки по общим категориям (страсть, эмоции, коммуникация, ценности, конфликт и восстановление, быт).
- Данные: матрица пар арканов 22×22 (253 уникальные неупорядоченные пары) как **фикстура/таблица** с оценками и подоценками, а не «магия в коде». Методика начисления оценок — **авторская**, открыто описана в документе; в продукте помечается как «символический слой».
- Тексты: `KnowledgeBlock` ключи `TAROT:arcana:<n>` (портрет аркана) и `TAROT:pair:<a>+<b>` (динамика пары), написаны своими словами, рефлексивно, с вопросами для разговора пары. Правила §4.4–4.5 действуют полностью.
- Запреты: предсказания событий (смерть, болезни, измены, беременность, финансы), «судьба решила», давление на решение о расставании.

**Иллюстрации.** Для MVP достаточно **22 Старших арканов**. Использовать собственную колоду в стиле продукта либо колоду с подтверждённым статусом общественного достояния (классическая Райдер–Уэйт–Смит 1909 года — проверить статус для целевых юрисдикций). Современные охраняемые колоды и арт конкурентов не использовать.

**Веса по умолчанию (с таро):** астрология 35% / психология 35% / нумерология 15% / таро 15%. Пользователь меняет ползунками; при отсутствии данных веса пересчитываются пропорционально (§3.4).

**Принцип «Мультивселенной» (ключевая фишка отчёта).**
- Каждый слой — отдельная «вселенная» со своим вердиктом и баллом: Астрология, Нумерология, Таро (символические) и Психология (научный слой).
- Общий балл — взвешенная сумма, но **главный экран показывает все вселенные рядом**.
- **Индекс согласия вселенных** = насколько оценки слоёв сходятся (считается детерминированно, например `100 − нормированный разброс`). Высокий — «вселенные сходятся»; низкий — подсвечиваются расхождения («астрология видит притяжение, психология — риск в конфликте») и объясняется, что это значит на практике.
- Честность: психология всегда помечается как научный слой и показывается отдельно, чтобы символические слои не «перекрывали» её.

**Вне MVP (не входят в скоринг, добавлять только по решению владельца):** расклады и «карта дня для пары» как отдельная развлекательная функция.

### 3.5. Прочие инженерные требования
- Идемпотентные Celery-задачи, ретраи, таймауты; статус генерации отчёта виден в UI (HTMX-polling/SSE).
- Rate limiting и кэширование LLM-ответов; стоимость вызова логируется.
- Версионирование алгоритма расчёта (`algorithm_version`) в каждом отчёте.
- Структурные логи, Sentry-совместимость, healthcheck.
- Безопасность: CSRF, валидация входа, шифрование чувствительных полей, подписанные токены для шаринга ссылок с TTL, возможность полного удаления данных.

## 4. ГИБРИДНЫЙ ИИ-СЛОЙ: БАЗА ЗНАНИЙ + МАТЕМАТИКА + LLM (без галлюцинаций)

### 4.1. Принцип
Модель **не знает** предметную область «из головы» и **не получает все книги в промт**. Работает схема:

**Математика (факты) → выбор блоков из базы знаний (retrieval) → LLM только оформляет и связывает → валидатор проверяет.**

- **Математика** (эфемериды, нумерология, скоринг) — детерминированный код. LLM ничего не считает.
- **База знаний** — наш собственный курируемый корпус интерпретаций (как у сервисов типа Лунника, но глубже): каждый блок короткий, атомарный, с ключом и источником.
- **LLM** получает **только** найденные блоки и факты текущей пары и обязана строить текст исключительно на них.

Вся база целиком в промт не помещается и не нужна: по каждому отчёту подтягивается лишь 20–60 релевантных блоков (по ключам аспектов, чисел, шкал). Это дешевле, точнее и проверяемо.

### 4.2. Приложение `knowledge/` (база знаний)
Модель `KnowledgeBlock`:
- `key` — детерминированный ключ, например `ASPECT:venus-trine-mars`, `NUM:life_path:3+7`, `ATTACH:anxious+avoidant`, `OCEAN:neuroticism:high+low`, `GOTTMAN:criticism:repair`, `TAROT:arcana:6`, `TAROT:pair:6+13`;
- `domain` — astrology / numerology / psychology / tarot;
- `locale` (ru/en), `version`, `status` (draft → reviewed → published);
- `text` — тезис 2–5 предложений: суть, проявление в паре, зона риска, практическая рекомендация;
- `evidence_level` — `scientific` (психология) / `symbolic` (астрология, нумерология) — используется в UI-метках и тоне;
- `sources` — список источников (автор, год, название, ссылка/DOI) — для scientific-блоков обязательно;
- `reviewed_by`, `reviewed_at`.

Выбор блоков — **по точным ключам** из расчётов (основной путь). Семантический поиск (pgvector) — только вспомогательный: для свободных вопросов пользователя и для связанных рекомендаций.

### 4.3. Как наполняем базу (важно: права и качество)
- **Книги и статьи нельзя загружать и воспроизводить целиком или близко к тексту** — это нарушение авторских прав. Допустимо: идеи, теории и факты (они не охраняются), записанные **нашими собственными словами**, со ссылкой на источник. Прямые цитаты — минимально и с атрибуцией.
- Приоритет источников для scientific-слоя: открытые работы и публикации (Big Five — Costa & McCrae, Goldberg и др.; теория привязанности — Bowlby, Ainsworth, Hazan & Shaver; исследования Готтмана), open-access статьи, общедоступные описания шкал. Всё приводим к нашему формату, не копируем.
- Для астрологии и нумерологии берём общеизвестные трактовки (классические значения аспектов, планет, домов, чисел) и пишем оригинальные тексты. Не копировать тексты конкурентов, включая Лунник.
- Конвейер наполнения: список ключей (матрица комбинаций) → черновики через LLM **на основании заданного тезиса и источников** → ручная вычитка эксперта → публикация. Статус `published` — единственный, который допускается в отчёты.
- Для психологии вычитка специалистом (психологом) обязательна до публикации.
- Контроль охвата: команда `manage.py kb_coverage` показывает, каких ключей в матрице не хватает; без блока отчёт выводит нейтральный текст, а не выдумку.

### 4.4. Защита от галлюцинаций (обязательные меры)
1. **Закрытый контекст.** В промт идёт только JSON: факты пары + найденные блоки с их `id`. Системное правило: «Используй только предоставленные блоки. Если данных нет — напиши, что данных недостаточно».
2. **Структурированный вывод.** Ответ — JSON по схеме: секции, а в каждом утверждении поле `block_ids` (на какие блоки опирается). Утверждение без ссылки отбрасывается.
3. **Пост-валидатор** (код, не LLM): проверяет, что все `block_ids` существуют, что в тексте нет планет/аспектов/чисел вне входных данных (сверка по словарю сущностей), что нет запрещённых формулировок («вам нельзя быть вместе», медицинские диагнозы, гарантии).
4. **Цифры не от модели.** Проценты, веса, графики берутся из движка и подставляются шаблоном.
5. **Ретрай и фолбэк.** При провале валидации — до 2 повторных попыток с указанием ошибки, затем фолбэк: отчёт собирается из готовых блоков без LLM-сшивки (всё равно красиво, потому что вёрстка у нас шаблонная).
6. **Температура низкая (0–0.3)**, фиксированная версия промпта и модели, логирование входа/выхода для регрессионных тестов.
7. **Кэш** по ключу «хэш входа + версия алгоритма + версия базы + версия промпта».
8. **Честная маркировка** в UI: «символический слой» и «научный слой» визуально различимы.

### 4.5. Роль LLM — что она делает и чего не делает
**Делает:** связывает блоки в цельный рассказ, подбирает порядок и акценты под конкретную пару, пишет вступление и резюме, адаптирует тон (тёплый, живой, с лёгким юмором), локализует RU/EN, формулирует план микропривычек **из рекомендаций найденных блоков**.
**Не делает:** не считает, не выдумывает аспекты/числа/исследования, не ссылается на «учёных доказали» без блока с источником, не даёт диагнозов и категоричных вердиктов, не использует клише («вселенная ведёт вас»).

### 4.6. Промпты
- Хранятся как версионируемые шаблоны (`insights/prompts/`), не вшиты в код; один шаблон — две локали через параметр.
- Структура: системные правила (§4.4–4.5) → схема вывода → факты пары → блоки знаний → запрос.
- Регрессионный набор: эталонные пары (в т.ч. крайние случаи) с проверкой, что вывод проходит валидатор и не содержит сущностей вне входа.

### 4.7. Результат для пользователя
Отчёт собирается из двух слоёв: **детерминированный каркас** (метрики, радар, таблица рисков, готовые блоки) и **персональная «сшивка» от LLM** (резюме, переходы, приоритизация). Даже если LLM недоступна — продукт работает и выглядит цельно.

12. **Визуальная ниша:** светлого, игривого и при этом дорогого по исполнению интерфейса с научной подачей на рынке нет.

## 6. ФАЗА 2 — ДИЗАЙН-СИСТЕМА (после анализа, до реализации UI)

Предыдущая версия («тёмный инженерный интерфейс в стиле Linear/Vercel») **отменена**. Новые вводные от владельца продукта:

- Интерфейс должен быть **игривым, лёгким, дружелюбным**.
- Но **по качеству исполнения — премиальным**: аккуратная типографика, выверенные отступы, плавные анимации, ни одного «дешёвого» элемента. Премиальность — в качестве, а не в мрачности и хай-теке.
- Не «эзотерика» (звёздное небо, мистические символы, фиолетовые градиенты) и не «сухой дашборд».

**Стартовая гипотеза (уточняется по итогам Фазы 1 и GATE 1):**
- Светлая тема по умолчанию (опционально тёмная), тёплые мягкие пастельные акценты, высокий контраст текста.
- Крупные скругления, мягкие тени, «карточный» интерфейс, плотность данных — через аккуратную иерархию, а не через мелкий шрифт.
- Характерный, но не детский шрифтовой дуэт (выразительный заголовочный + нейтральный текстовый с поддержкой кириллицы).
- Оригинальные иллюстрации/абстрактные формы и маскот или графический мотив партнёров (двое — форма/цвет), без заимствования чужих персонажей и брендов.
- Анимации: плавные переходы, «оживающие» шкалы и радар, приятный экран ожидания генерации, уважение к `prefers-reduced-motion`.
- Цвет несёт смысл: синергия / нейтрально / внимание / риск — единая семантическая палитра, доступная для дальтоников (не только цвет, но и иконка/подпись).

### Что дизайн-система обязана закрыть по итогам анализа конкурентов
- **Карточки категорий совместимости** (цвет + иконка + короткий вердикт) вместо одного большого числа; общий балл — вторичен.

- **Паттерн «Почему так»:** раскрывающаяся «улика» под каждым выводом (аспект / число / шкала + метка символический/научный слой).
- **Шеринг-карточка пары** (формат под Telegram/сторис): тип пары, 3 категории, QR/ссылка.
- **Степпер входа из 3 режимов** (быстрый / расширенный / глубокий) с видимым «вы уже получили X, добавьте время рождения — получите Y».
- **Парный режим:** экраны приглашения партнёра, ожидания, «ответили оба».
- **Ежедневный слой:** карточка «вопрос дня» и «микропривычка дня», streak без давления.

- **Состояния:** пустые, ошибки, «не хватает данных», «точность оценки».

## 7. ФАЗА 3 — ПОЛНЫЙ КЛИКАБЕЛЬНЫЙ UI-ПРОТОТИП (UI-first, бэкенд-логика НЕ пишется)

**Решение владельца:** сначала делаем **полный интерфейс со всеми кнопками, экранами и состояниями**, и только потом подключаем настоящий бэкенд.

### 7.1. Принципы
- Прототип — это уже **настоящий Django-проект** (не одноразовая картинка): те же шаблоны, компоненты, URL и представления, которые останутся в продукте.
- Вся «умная» логика подменяется **заглушками за теми же интерфейсами**, что будут у боевого бэкенда (Dependency Inversion, §3.2). Например: `ReportProvider` (Protocol) → сейчас `FakeReportProvider` (читает JSON-фикстуры, с задержкой и случайными состояниями), потом `RealReportProvider`. Подключение бэкенда = замена реализации в composition root, **без правки шаблонов и views**.
- Контракт данных фиксируется заранее: **схемы DTO / JSON-контракты** (`docs/contracts/*.md` + pydantic-модели). Фикстуры строго соответствуют контракту, поэтому интеграция потом не ломает UI.
- Никаких мёртвых кнопок: любая кнопка либо ведёт на экран, либо показывает осмысленное демо-состояние (модальное окно «демо», тост, ошибка, пустое состояние).
- Авторизация, оплата, LLM, эфемериды — в прототипе имитируются (демо-вход, фейковый пейволл с понятным «это демо»).

### 7.2. Обязательная карта экранов и состояний (ничего не пропускать)
1. **Лендинг:** hero с живым мини-демо, как это работает (4 «вселенной»: астрология / числа / таро / психология), примеры отчёта, «типы пар», FAQ, дисклеймер, CTA.
2. **Быстрый старт:** только даты рождения двух людей → мгновенный «первый результат» (мини-отчёт).
3. **Мастер ввода (3 режима):** быстрый / расширенный (время, место с автоподсказкой города) / глубокий (психо-анкеты). Валидация, подсказки, состояние «не знаю время рождения».
4. **Анкеты психологии:** OCEAN (короткая версия), тип привязанности, реакции на стресс/конфликт, MBTI (опционально); прогресс, «сохранить и продолжить».
5. **Настройка весов:** ползунки (астрология / психология / числа / таро) с живым пересчётом демо-балла, кнопка «сбросить».
6. **Экран ожидания генерации:** пошаговый «живой» прогресс.
7. **Дашборд результата:** общий балл + **панель «Мультивселенная» (4 слоя рядом + индекс согласия)** + **категории с цветом и иконкой**, радар, шкалы синергии, зоны трения, «точность оценки», метки «символический/научный слой».
8. **Вкладки глубокого разбора:** Астрология / Психология (триггеры Готтмана, привязанность) / Числа и Матрица судьбы / Таро (аркан-слой) / План микропривычек. В каждом выводе — «Почему так» (раскрывающаяся улика).
9. **Тип пары + шеринг-карточка:** предпросмотр картинки, копирование ссылки, «поделиться в Telegram» (демо).
10. **Парный режим:** приглашение партнёра (ссылка/код), ожидание, «ответили оба», общий разбор.
11. **Ежедневный слой:** вопрос дня, микропривычка дня, streak.
11а. **Таро-вселенная:** карточки арканов обоих партнёров и аркана пары (с иллюстрациями), тип связи между арканами, трактовка с вопросами для разговора пары, «Почему так» (как считался аркан), метка «символический слой», состояние «нет даты рождения».
12. **История отчётов, профили партнёров** (список, редактирование, удаление данных — требование приватности).
13. **PDF-версия отчёта** (вёрстка HTML для печати) и кнопка экспорта (демо).
14. **Пейволл и тарифы:** «бесплатно / глубокий разбор», прозрачная цена, без тёмных паттернов.
15. **Аккаунт:** вход/регистрация (демо), настройки, язык RU/EN, согласия, удаление данных.
16. **Служебные состояния:** пустые, ошибка, нет интернета, «не хватает данных», 404/500, согласие на cookie, дисклеймер.

## 8.1. ФАЗА 5 — ПОДКЛЮЧЕНИЕ БЭКЕНДА ПО ВЕРТИКАЛЬНЫМ СРЕЗАМ

Реализуем не «весь бэкенд, потом весь фронт», а **тонкими вертикальными срезами**. В каждом срезе `Fake…Provider` из прототипа заменяется настоящей реализацией, а UI остаётся без изменений; каждый срез — рабочий и протестированный:

1. **Срез A — Нумерология** (самый простой, чистые функции): ввод → расчёт → скоринг → карточка в UI. Служит эталоном архитектуры.
2. **Срез B — Астрология:** геокодинг и таймзона → натальная карта → аспекты синастрии → скоринг (Венера/Марс, Луна, Сатурн, обработка отсутствия времени рождения).
3. **Срез C — Психология:** анкеты OCEAN, тип привязанности, Готтман-индикаторы, MBTI (опционально) → скоринг.
4. **Срез D — Движок и веса:** реестр скореров, динамическое перераспределение, ползунки в UI.
5. **Срез E0 — База знаний:** модель `KnowledgeBlock`, матрица ключей, админка с ревью-статусами, импорт/экспорт фикстур, `kb_coverage`, первые черновики по нумерологии и психологии.
5. **Срез E — ИИ-инсайты:** retrieval блоков по ключам, пайплайн, промпты со схемой вывода, пост-валидатор, фолбэк без LLM, Celery, статус генерации.

## 9. ФАЗА 6 — ТЕСТИРОВАНИЕ И ПОЛИРОВКА

- **Валидность расчётов:** сверка натальных карт с эталонными (Astro.com / Swiss Ephemeris) на наборе известных дат; сверка нумерологических формул с зафиксированными правилами (какую систему используем — Пифагор / халдейская — зафиксировать в ADR).
- **Крайние случаи:** неизвестное время рождения, высокие широты, переход часовых поясов и летнее время, полночь, одинаковые даты, мастер-числа (11/22/33), редукция аркана для значений > 22 и мастер-дат, неполные психоданные.
- **Тесты:** unit (домен, скореры), integration (use cases + БД), e2e ключевых сценариев, тесты на детерминизм и версионирование алгоритма.
- **Производительность:** время до первого результата (быстрые метрики сразу, ИИ-тексты — потоково/по готовности), индексы БД, N+1, кэш.
- **Качество ИИ-текстов:** набор регрессионных кейсов, проверка на «выдуманные» аспекты и клише.
- **UX/доступность:** Lighthouse, WCAG AA, мобильная проверка, reduced-motion.
